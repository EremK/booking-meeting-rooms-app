# Бронювання переговорних

Невеликий веб-застосунок для бронювання переговорних кімнат в офісі.
Співробітник відкриває тижневий розклад кімнати, бачить зайняті слоти,
бронює вільний час і може скасувати власне бронювання. Чуже бронювання
не можна скасувати ні через інтерфейс, ні прямим запитом до API.

## Стек

- **Мова:** TypeScript (strict mode) в обох воркспейсах.
- **Фронтенд:** React + Vite, звичайний CSS Modules (без Tailwind і
  UI-кітів). Сітка розкладу написана вручну — без FullCalendar чи
  подібних бібліотек.
- **Бекенд:** NestJS.
- **База даних:** PostgreSQL, доступ через Prisma.
- **Автентифікація:** JWT у HttpOnly-кукі.
- **Тести:** Jest (бекенд).

Репозиторій — npm workspaces монорепо: `frontend/` та `backend/`.

## Вимоги

- Node.js 22+ і npm 10+
- PostgreSQL 14+ (локально встановлений або запущений у Docker)

## Запуск через Docker Compose (найшвидший спосіб)

Піднімає PostgreSQL, бекенд і фронтенд одразу трьома контейнерами. Файлів
`.env` створювати не потрібно — усі змінні вже задані в
`docker-compose.yml`.

```bash
docker compose up --build -d
```

Застосувати сіди (окремим кроком, оскільки сід перезаписує демо-дані —
автоматично на кожному старті це було б несподіваним):

```bash
docker compose exec backend npm run db:seed
```

Відкрити [http://localhost:5173](http://localhost:5173). Міграції бази
застосовуються бекендом автоматично при кожному старті контейнера.

Щоб зупинити: `docker compose down` (дані PostgreSQL зберігаються в
іменованому томі; додай `-v`, щоб видалити і їх).

Нижче — альтернативний спосіб запуску без Docker, з бекендом і
фронтендом напряму через Node.js.

## Швидкий старт

### 1. Встановити залежності

```bash
npm install
```

Команда встановлює залежності обох воркспейсів і автоматично генерує
Prisma Client (`postinstall` у `backend/`).

### 2. Підняти PostgreSQL

Підійде будь-який локальний інстанс. Якщо його немає під рукою, можна
одразу підняти тимчасовий контейнер:

```bash
docker run -d --name booking-postgres \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=booking_meeting_rooms \
  -p 5432:5432 postgres:16-alpine
```

### 3. Налаштувати змінні середовища

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Значення за замовчуванням у `backend/.env.example` відповідають
контейнеру з кроку 2. Якщо PostgreSQL слухає інший порт/хост — постав
свій `DATABASE_URL`. Повний опис змінних — у розділі
[«Змінні середовища»](#змінні-середовища) нижче.

### 4. Застосувати міграції та сіди

```bash
npm run db:migrate --workspace backend
npm run db:seed --workspace backend
```

Сід створює 6 кімнат, двох тестових користувачів і кілька демонстраційних
бронювань (відносно поточної дати, тож завжди виглядають актуально).

### 5. Запустити застосунок

У двох окремих терміналах:

```bash
npm run dev:backend    # http://localhost:3000
npm run dev:frontend   # http://localhost:5173
```

Відкрити [http://localhost:5173](http://localhost:5173).

## Змінні середовища

**`backend/.env`**

| Змінна | Призначення |
|---|---|
| `DATABASE_URL` | Рядок підключення до PostgreSQL |
| `PORT` | Порт, на якому слухає бекенд (за замовчуванням `3000`) |
| `NODE_ENV` | `development` / `production` — впливає на прапорець `Secure` у кукі сесії |
| `FRONTEND_ORIGIN` | Origin фронтенда, дозволений у CORS |
| `JWT_SECRET` | Секрет для підпису сесійного JWT |
| `JWT_EXPIRES_IN_SECONDS` | Термін дії сесії в секундах |

**`frontend/.env`**

| Змінна | Призначення |
|---|---|
| `VITE_API_URL` | Базова адреса бекенд-API |

## Як влаштована перевірка перетинів

Перетин двох інтервалів перевіряється однією чистою функцією
(`intervalsOverlap` у `backend/src/bookings/interval-overlap.ts`) за
класичною формулою напіввідкритого інтервалу `[start, end)`:
`a.start < b.end && b.start < a.end`. Завдяки цьому бронювання впритул
(10:00–11:00 і 11:00–12:00) коректно не вважаються конфліктом — саме
цей випадок, разом із частковим перекриттям, повним збігом і
бронюваннями в сусідні дні, покритий юніт-тестами. При створенні
бронювання бекенд підвантажує активні (нескасовані) бронювання тієї ж
кімнати за той самий офісний день і прогонює кандидата через цю ж
функцію — жодної окремої SQL-логіки для перевірки перетину немає, вся
семантика перевірена один раз і використовується скрізь.

## Як зберігається час

У базі даних час завжди зберігається в UTC (`timestamptz` у
PostgreSQL) — жодних наївних міток часу без часового поясу. Робочі
години офісу (09:00–19:00) і кратність 30 хвилинам перевіряються на
бекенді через конвертацію UTC-моменту в час `Europe/Kyiv` (бібліотека
Luxon, з урахуванням переходу на літній/зимовий час), незалежно від
того, з якого часового поясу прийшов запит. На фронтенді час завжди
показується в поясі користувача, визначеному браузером
(`Intl.DateTimeFormat`); сітка розкладу структурно прив'язана до
київських календарних днів (тобто дні тижня — це київські дні), а
підписи годин і самих бронювань лише переформатовуються в пояс
користувача для відображення. Якщо пояс користувача відрізняється від
київського, інтерфейс явно про це повідомляє поруч із сіткою.
