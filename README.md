# Бронювання переговорних

Невеликий веб-застосунок для бронювання переговорних кімнат в офісі.
Співробітник відкриває тижневий розклад кімнати, бачить зайняті слоти,
бронює вільний час і може скасувати власне бронювання. Чуже бронювання
не можна скасувати ні через інтерфейс, ні прямим запитом до API.

## Основні можливості

- Реєстрація та вхід; сесія — JWT у HttpOnly-кукі, зберігається після
  перезавантаження сторінки.
- Список кімнат з поточним статусом (вільна/зайнята), фільтром за
  місткістю та посиланням на розклад.
- Тижнева сітка розкладу кожної кімнати: верстка вручну (без
  FullCalendar чи подібних бібліотек), гортання тижнів вперед і назад,
  виділення поточного дня й часу, свої бронювання видно окремо від
  чужих.
- Час усюди показується в поясі користувача, визначеному браузером;
  якщо він відрізняється від київського, це видно поруч із сіткою.
- Створення бронювання — разового або серії з щотижневим повторенням —
  із серверною валідацією: робочі години, крок і тривалість, відсутність
  перетинів.
- Скасування свого бронювання (одного випадку або всієї серії) з
  підтвердженням; чуже бронювання скасувати не можна ні з інтерфейсу,
  ні напряму через API.
- «Мої бронювання»: майбутні, минулі й скасовані бронювання окремими
  вкладками з пагінацією.
- Підтвердження email у dev-режимі: без підтвердженого email бронювати
  не можна, посилання підтвердження друкується в лог сервера.
- Сповіщення в застосунку (дзвіночок і тост) за N хвилин до кінця
  бронювання, якщо наступний слот у тій самій кімнаті вже зайнятий.

## Стек

- **Мова:** TypeScript (strict mode) в обох воркспейсах.
- **Фронтенд:** React + Vite, звичайний CSS Modules (без Tailwind і
  UI-кітів). Сітка розкладу написана вручну — без FullCalendar чи
  подібних бібліотек.
- **Бекенд:** NestJS.
- **База даних:** PostgreSQL, доступ через Prisma.
- **Автентифікація:** JWT у HttpOnly-кукі.
- **Тести:** Jest (бекенд).

Репозиторій — npm workspaces монорепо: `frontend/` та `backend/`.

## Вимоги

- Node.js 22+ і npm 10+
- PostgreSQL 14+ (локально встановлений або запущений у Docker)

## Запуск через Docker Compose (найшвидший спосіб)

Піднімає PostgreSQL, бекенд і фронтенд одразу трьома контейнерами. Файлів
`.env` створювати не потрібно — усі змінні вже задані в
`docker-compose.yml`.

```bash
docker compose up --build -d
```

Застосувати сіди (окремим кроком, оскільки сід перезаписує демо-дані —
автоматично на кожному старті це було б несподіваним):

```bash
docker compose exec backend npm run db:seed
```

Відкрити [http://localhost:5173](http://localhost:5173). Міграції бази
застосовуються бекендом автоматично при кожному старті контейнера.

Щоб зупинити: `docker compose down` (дані PostgreSQL зберігаються в
іменованому томі; додай `-v`, щоб видалити і їх).

Нижче — альтернативний спосіб запуску без Docker, з бекендом і
фронтендом напряму через Node.js.

## Швидкий старт

### 1. Встановити залежності

```bash
npm install
```

Команда встановлює залежності обох воркспейсів і автоматично генерує
Prisma Client (`postinstall` у `backend/`).

### 2. Підняти PostgreSQL

Підійде будь-який локальний інстанс. Якщо його немає під рукою, можна
одразу підняти тимчасовий контейнер:

```bash
docker run -d --name booking-postgres \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=booking_meeting_rooms \
  -p 5432:5432 postgres:16-alpine
```

### 3. Налаштувати змінні середовища

```bash
cp backend/.env.example backend/.env
cp frontend/.env.example frontend/.env
```

Значення за замовчуванням у `backend/.env.example` відповідають
контейнеру з кроку 2. Якщо PostgreSQL слухає інший порт/хост — постав
свій `DATABASE_URL`. Повний опис змінних — у розділі
[«Змінні середовища»](#змінні-середовища) нижче.

### 4. Застосувати міграції та сіди

```bash
npm run db:migrate --workspace backend
npm run db:seed --workspace backend
```

Сід створює 6 кімнат, двох тестових користувачів і 21 демонстраційне
бронювання: кілька минулих (для вкладки «Минулі») і принаймні одне на
кожен з наступних 14 днів (щоб розклад виглядав живим при гортанні
тижнів вперед). Дати рахуються відносно моменту запуску сіда, тож
завжди актуальні.

### 5. Запустити застосунок

У двох окремих терміналах:

```bash
npm run dev:backend    # http://localhost:3000
npm run dev:frontend   # http://localhost:5173
```

Відкрити [http://localhost:5173](http://localhost:5173).

## Тести

```bash
npm test
```

Запускає юніт-тести бекенда (перевірка перетинів інтервалів, валідація
бронювань, робочі години, авторизація) з кореня репозиторію. Не потребує
підключення до бази даних.

Окремо, з `backend/` (потребує запущеного PostgreSQL з застосованими
міграціями):

```bash
npm run test:e2e
```

Містить наскрізні тести проти реального застосунку та бази: захист від
гонки (два одночасні запити на той самий слот — рівно один встигає) і
основні API-сценарії бронювання — створення, скасування (включно з
перевіркою власності) та відмови валідації (зайнятий слот, поза робочими
годинами, у минулому, некоректна тривалість/назва).

## Як влаштована перевірка перетинів

Перетин двох інтервалів перевіряється однією чистою функцією
(`intervalsOverlap` у `backend/src/bookings/interval-overlap.ts`) за
класичною формулою напіввідкритого інтервалу `[start, end)`:
`a.start < b.end && b.start < a.end`. Завдяки цьому бронювання впритул
(10:00–11:00 і 11:00–12:00) коректно не вважаються конфліктом — саме
цей випадок, разом із частковим перекриттям, повним збігом і
бронюваннями в сусідні дні, покритий юніт-тестами. При створенні
бронювання бекенд підвантажує активні (нескасовані) бронювання тієї ж
кімнати за той самий офісний день і прогонює кандидата через цю ж
функцію — жодної окремої SQL-логіки для перевірки перетину немає, вся
семантика перевірена один раз і використовується скрізь.

## Захист від гонки (race condition)

Перевірка перетину вище — це окремий SELECT перед INSERT, а не атомарна
операція: два запити на той самий слот можуть обидва пройти цю перевірку
до того, як хоч один з них зафіксується в базі. Тому справжня гарантія —
це `EXCLUDE`-обмеження на рівні PostgreSQL (`bookings_no_overlap`,
міграція `add_booking_overlap_exclusion_constraint`):

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "bookings"
  ADD CONSTRAINT "bookings_no_overlap"
  EXCLUDE USING gist (
    "roomId" WITH =,
    tstzrange("startAt", "endAt", '[)') WITH &&
  )
  WHERE ("cancelledAt" IS NULL);
```

Постгрес атомарно відхиляє другий INSERT, якщо його діапазон
`tstzrange("startAt", "endAt", '[)')` перетинається з уже наявним активним
бронюванням тієї ж кімнати — без жодного блокування на рівні застосунку.
`WHERE ("cancelledAt" IS NULL)` виключає скасовані бронювання з перевірки,
тож скасований слот одразу стає вільним. Межі `[start, end)` узгоджені з
правилом впритул: 10:00–11:00 і 11:00–12:00 не перетинаються.

Бекенд ловить відхилення цього обмеження (`BookingsService.createBooking`)
і перетворює його на те саме зрозуміле повідомлення «Цей час уже
заброньовано», що й швидка перевірка вище, — користувач ніколи не бачить
сиру помилку бази даних. Поведінка перевірена наскрізним тестом
(`backend/test/booking-race-condition.e2e-spec.ts`): два одночасні HTTP-запити
на бронювання того самого слоту — рівно один отримує `201`, інший `409`, і
в базі залишається рівно один запис.

## Як зберігається час

У базі даних час завжди зберігається в UTC (`timestamptz` у
PostgreSQL) — жодних наївних міток часу без часового поясу. Робочі
години офісу (09:00–19:00) і кратність 30 хвилинам перевіряються на
бекенді через конвертацію UTC-моменту в час `Europe/Kyiv` (бібліотека
Luxon, з урахуванням переходу на літній/зимовий час), незалежно від
того, з якого часового поясу прийшов запит.

На фронтенді час завжди показується в поясі користувача, визначеному
браузером (`Intl.DateTimeFormat().resolvedOptions().timeZone`). Сітка
розкладу при цьому структурно прив'язана до київських календарних днів
і офісних слотів — колонки тижня це київські дні, а позиція бронювання
в сітці рахується за київським часом. Підписи годин зліва від сітки та
час усередині кожного бронювання окремо переформатовуються в пояс
користувача для відображення: той самий слот 10:00–10:30 за Києвом
з'явиться в тому самому рядку сітки, але з підписом «09:00–09:30» для
користувача в Берліні. Якщо пояс користувача відрізняється від
київського, інтерфейс явно повідомляє про це поруч із сіткою.
